<methodology>
## 覆盖维度（逐条过筛，不得只做正常场景）

1. **正常场景**：每个功能的最短正向主路径至少 1 个测试点——"太显然"不是省略理由。
2. **边界值**：空值 / 最小 / 最小-1 / 最大 / 最大+1 / 超大 / 特殊字符 / 负数。
   **时间类规则必须双侧**：每条时限/有效期/超时/自动触发规则都要"边界前一拍可成功"
   与"到达后进入另一态"两个测试点——给定数值不等于已验证。
3. **异常场景**：网络中断、服务超时、权限不足、依赖不可用、失败后重试。
4. **权限与角色**：每个角色能做什么、不能做什么；越权访问。
5. **数据一致性**：写入后读回一致、并发写、脏数据残留。
6. **逆向操作成对**：创建↔删除、分配↔释放、导入↔撤销，每对都要有测试点。
7. **二阶交叉**（存量缺陷高发区，必做）：
   - 写入路径 × 校验规则：同一条校验在 创建 / 编辑 / 重新提交 / 导入 各路径是否都生效
   - 失败 × 重试：每种拦截发生后，重试能否恢复
   - 标识 × 重复：名称 / 编号等唯一性字段重复提交的行为

## 测试类型的判定

test_type 只能取：功能 / 性能 / 安全 / 兼容性。
- 类型域策略里判为 include 的轴（如并发、可靠、安全、兼容），映射到最接近的这四个值之一，
  并在名称里用方括号标签标注来源轴：如"[并发] 同一账户并发下单"。
- 纯功能性的测试点一律"功能"，不要为了凑类型硬分。

## 优先级判定（严格执行，避免全部高优先级）

- **P0（冒烟）**：必须同时满足——主流程的核心路径 + 失败则整个功能不可用。
  逐条自检："这条测试点如果不测，用户能否完成核心操作？"答案为"否"才是 P0。
- **P1（常规）**：正常功能验证 + 常见异常处理。
- **P2（边界）**：极端输入、低频场景、需特殊环境。
- **P3（可选）**：锦上添花、成本远高于收益的项，尽量少用。

P0 占比控制在 20% 以内。测试策略中存在 Risk Map 时按映射建议执行：
Critical → 必须有 P0；High → P0/P1；Medium → P1；Low → P2 或按需。
