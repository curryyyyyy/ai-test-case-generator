<methodology>
## 用例编号

`TC-{{两位模块号}}-{{两位序号}}`，模块号对应大纲中的模块顺序（第 1 个模块 → TC-01-xx）。
P0 冒烟用例在名称末尾追加 `（SMOKE-n）`，n 为冒烟序号，非 P0 不标。

## 正文格式（按被测功能有无 UI 二选一）

**有 UI 的功能**——四段式：

- 前置条件: 本条特有的前置（同模块共享的前置不要重复写）
- 操作步骤: 1. 进入{{页面，含从哪里到达}} 2. 填写{{字段与具体值}} 3. 点击{{按钮}}
- 预期结果: {{页面上能观察到的明确现象}}

**无 UI 的后端功能**（数据 stage / 定时任务 / 消息队列 / SDK）——协作五段式：

- 前置条件: 已准备的数据
- 操作步骤（请开发执行）: 具体触发方式
- 预期结果（请开发反馈）: 明确唯一的可观察结果
- 验证方式: 开发查库 / 查日志的具体位置与反馈内容

被测功能无 UI 时**不要照抄 UI 用例写"操作步骤"**——测试无法独立执行，步骤会悬空。

## 可执行性硬标准（逐条自检，违反即不可交付）

1. **嵌入具体数据**：用真实的编号、字段名、字段值，禁止写 `{{xxx}}`、`"某数据"` 这类占位符。
   生成的数据要满足文档声明的字段约束（长度上限、枚举、格式），且不顶格。
2. **页面可达性**：每个页面/入口首次出现时写清从哪里到达（如"后台 → 营销中台 → 活动列表"）。
   文档中未说明入口时，不得只写"打开 XX 页"蒙混——写"TODO：入口待确认"。
3. **异步行为必含判定时限**：预期结果含"自动变为/稍后更新/异步生效"时，必须写明
   等待多久不发生即判失败（如"5 分钟内自动变为已结束，超过 5 分钟未变判失败"）。
4. **一条用例只测一个点**：预期结果明确唯一，不写"或 A 或 B"——应拆成两条。
5. **断言不超出验证强度**：两个样本证不了"全局唯一"，名称应改为"不同对象的编号互不相同"。
6. **正文零代码内部**：禁止出现 `文件:行`、SDK 符号、错误码常量、实现术语
   （如 `resp.Code != 0`、`return nil`）。一律改业务语言：
   `resp.Code != 0` → "服务端返回业务错误"。
   允许保留：接口名、配置项 key、业务字段名、业务枚举值、可观察的日志原文。
7. **失败之后要有重试**：每种失败 / 拦截场景，配"失败 → 再试 → 恢复"的用例。

## 风险追溯

存在 Risk Map 时，每条用例的 risk_ref 填其验证的风险编号（R1、R2…）；
Critical 与 High 风险必须被至少一条用例覆盖，无对应风险时留空字符串。
evidence_source 填本用例的文档依据（章节标题）。

## 输出预算纪律

用例数上限 `min(测试点数 × 1.5, 80)` 条。超出时按 P0 > P1 > P2 收缩，
**不要省略四段式去凑数量**——一条残缺的用例不如不写。

<constraints>
1. case_id 唯一且连续，格式为 TC-{{两位模块号}}-{{两位序号}}。
2. directory 体现模块路径（如"登录/鉴权""下单/支付"）。
3. case_level 仅可为 P0/P1/P2/P3，且与测试点的优先级保持一致。
4. steps 至少 2 步，每步描述清晰可执行，用具体数据而非占位符。
5. tags 只填两类合法值：可测试性标注（需真机/需Mock/需专业环境）
   或类型域轴标签（并发/可靠/安全/兼容/迁移/集成/国际化）；无标签时留空列表。
6. 不要输出解释文字。
</constraints>
