<methodology>
按十个字段抽取需求模型。每个字段的口径：

1. goal：需求目标（一句话）+ 成功标准（可判定的完成条件）。
2. scope_in：功能范围，逐条列具体功能点。
3. scope_out：明确的"非目标"声明。**必须单独收录**——非目标决定测试边界，
   且每条非目标在下游都应转化为一条"限制的验证"。文档没写非目标时，
   把"文档隐含排除但易被误认为支持的场景"也列在这里，并注明"文档未显式声明"。
4. roles：角色 × 能做什么 / 不能做什么（这是权限矩阵的雏形）。
5. inputs / outputs：数据从哪来、到哪去、谁消费。
   **无下游消费的 output 是重要的证伪线索**，必须在 rules 或 open_questions 中点出。
6. states：状态与流转，逐条写成"状态A --事件--> 状态B"的形式。
7. rules：业务规则逐条编号，**每条必须带 evidence**（文档章节名）。
8. exceptions：异常/错误场景下的预期行为。
9. dependencies：上下游系统、共享数据、时序依赖。
10. open_questions：模糊 / 缺失 / 矛盾项。**不硬猜**——宁可留空提问，不要编造规则填入 rules。

抽取时的三个高发漏点，逐项过筛：
- **FAQ / 常见问答段落**：每一个问答都是一条潜在的业务规则或边界。
- **"非目标"声明**：常写在文档末尾或被忽略的段落。
- **NFR 定性描述**：出现"快""稳定""支持多端""高并发"这类没有数值的描述时，
  不要放行——要么在 open_questions 里问到具体指标，要么显式记录"本版不验证"。
</methodology>

<evidence_rules>
证据等级（见 core/evidence.md）：
- E1 文档证据：需求文档 / 设计文档 / API 文档 / FAQ 的章节。本阶段无代码仓库，
  evidence_level 一律取 E1，evidence_source 填具体的章节标题（不是"文档"这种泛化词）。
- 结论状态：文档明确写明的记 fact；由文档合理推断的记 inference；
  文档没写但按业务常识应当存在的记 hypothesis。

禁止不加标注直接写"这里有问题"——每条 rules / exceptions 都要能追溯到文档位置。
</evidence_rules>

<instruction>
严格按上述十个字段输出结构化需求模型。抽不到内容的字段留空列表，
不要为了凑数编造内容，也不要输出与需求无关的泛化建议。
</instruction>

<constraints>
1. 语言使用中文。
2. rules 每条必须填 evidence_source（章节标题），无法定位来源的规则不要写入。
3. open_questions 每条必须给 suggestion（你的建议选项或建议数值），
   让用户能一句话裁决，而不是开放式提问。
4. states 用"状态A --事件--> 状态B"的统一句式，不要用自然语言散述。
5. 内容要可直接用于后续的测试策略与用例设计。
</constraints>
